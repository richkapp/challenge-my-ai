# Platform pairing and revocation

## Authentication decision

The launch pairing service uses owner-bound Ed25519 public-key authentication, not a bearer client secret. This matches `CMAI_AGENT_PROTOCOL_V1`: the platform stores only public keys, while each Hermes or OpenClaw adapter keeps its private key locally. Every pairing must request `challenge:read`, `challenge:run`, and `pairing:manage`; it may receive only scopes allowed by its one-time code. Card 07A adapters omit `contribution:submit`, so their persisted keys cannot submit. A later Card 08 flow must request and disclose that added authority explicitly.

## Pairing flow

1. An authenticated account session creates a five-minute pairing code with `POST /api/agent/pair/code`. Cookie/Supabase sessions require same-origin CSRF.
2. Codes contain 160 bits of randomness, are returned once, and are stored only as domain-separated SHA-256 hashes. New codes cancel older unused codes for the same owner/runtime.
3. The local adapter redeems the code through `POST /api/agent/pair` with one strict `pair.create` envelope. The code binds the owner, runtime, and normalized device label. Redemption is atomic and single-use.
4. Later adapter requests are signed with Ed25519 canonical protocol bytes. `PairingService.authorizeAndExecute()` reads authoritative state under the same local/Postgres transaction lock used by revocation, so consumers do not rely on a cached active status.
5. The current active key signs `POST /api/agent/pair/rotate`. Rotation retires the old key and activates exactly one higher-generation replacement with no dual-active grace window.
6. The paired client can call `POST /api/agent/revoke`; the authenticated owner can call `POST /api/agent/revoke/:id`. Revocation is server-authoritative and immediately invalidates later protected actions.

Authenticated owners can list devices and redacted audit events with `GET /api/agent/pair`, and rename their own active device with `PATCH /api/agent/pair/:id`. Foreign and unknown IDs return the same not-found response. Pairing codes are rejected from GET query strings and never enter audit or telemetry payloads.

## Persistence and concurrency

`MemoryPairingStateBackend` is the local/preview backend. Runtime local mode coordinates pairing and Agent-feed working copies as one provisional transaction, validates cross-store replay coherence before and after the protected action, and commits both copies only after validation. `PostgresPairingStateBackend` requires the explicit reviewed Agent Protocol migration, performs SELECT-only reads, stores schema-versioned JSONB, locks the pairing row and then `cmai_state`, and validates cross-store replay coherence before and after every protected action. The feed state is now schema v2: the v2 migration upgrades populated v1 accepted submissions by reconstructing their exact request aliases from matching pairing authorization receipts, preserving contribution and consumed-grant truth, and marking their payload identity as legacy request-bound. It first validates every legacy read receipt/cache/authorization relationship in linear indexed passes against all v2 replay invariants except the new per-pair ceilings, including response audience, truthful serialized bytes, unique cache ownership, and exact one-to-one cross-row cardinality; a maximum live 10,000-record reserve across twenty quota-valid pairings is regression-tested through the final v2 validator under a bounded migration-time budget, and malformed expired evidence is refused rather than erased. It then captures one transaction timestamp, atomically removes only canonically expired read receipt/cache/authorization triples from both locked rows, and refuses live legacy per-pair overflow with an explicit drain-and-retry timestamp. Unexpired exact replay evidence is never evicted to force migration; once the canonical 30-minute window drains, rerunning the migration succeeds without manual JSON repair. Migrated legacy submissions retain exact request replay but conservatively reject fresh-request business aliases because v1 never persisted enough canonical payload evidence to prove them safe. Both backends execute the same service state machine. Pairing-code redemption, key rotation, revocation, and protected-action authorization are linearizable within that transaction boundary.

Expired code hashes are retained for 24 hours, exact read receipts for 30 minutes, exact contribution-submit request aliases and business receipts for 30 days, and redacted audit events for 365 days. New v2 submission idempotency is keyed by the canonical business payload, so a fresh signed `request_id` can alias the original accepted submission without re-running it. Every accepted, replayed, or terminal submission result records one feed-side request receipt before pairing authorization commits; exact signed retries return that stored outcome without re-running business logic. Every request receipt has one matching pairing authorization receipt with the same canonical operation-specific retention window and exact absolute creation and expiry timestamps. Persisted validators enforce those windows plus the read, submission, aggregate, and per-pairing reserves instead of trusting service-time checks alone. The mandatory end-to-end read replay-evidence reserve is 10,000 records, submission replay evidence has a separate 50,000-record reserve, and the combined persisted bound is 60,000 records. Submission evidence is additionally capped at 5,000 records per pairing. Read response evidence is bounded by a shared 10,000-record / 32 MiB cache and a 500-record / 1 MiB cache ceiling per pairing, so one pairing cannot exhaust another pairing's count or byte admission. Exact replay runs before every capacity check. Durable rate-limit state is capped at 10,000 active buckets per capacity class and 60,000 in aggregate. Capacity fails closed instead of silently evicting replay or revocation evidence or allowing one principal or operation class to consume another class's replay reserve. `bun run prove:agent-feed-postgres:disposable` is the committed failure-safe loopback harness; `bun run prove:agent-feed-postgres:failures` exercises its committed ambiguous-client and HUP/INT/TERM interruption matrix behind an explicit master test gate; unsupported signals are rejected before any resource creation and the cleanup hook cannot abort deletion, while ambient hook variables are inert on the normal proof path. The harness creates a UUID-named role/database, verifies pre-create absence, records cleanup intent before each external create, atomically marks the role with a generated ownership token, verifies exact role/database ownership before deletion, defers catchable termination signals across each create-plus-publication boundary, ignores further catchable termination during cleanup, authenticates through the generated credential and asserts `current_user`/`current_database`, runs migration/concurrency/fairness proofs including transactional count and >1 MiB v1 overflow paths, instruments the production challenge executor directly, then drops and verifies absence of both temporary resources even on failure.

## Security boundaries

- No private key, provider API key, OAuth token, refresh token, cookie, or provider credential enters pairing state.
- Pair responses omit owner IDs and public-key values. Owner audit responses omit owner IDs, pairing codes, signatures, labels, and key material.
- Redeem failures deliberately collapse invalid, expired, consumed, cancelled, runtime-mismatched, and label-mismatched codes into one `pairing_not_found` response.
- Durable rate-limit buckets store only hashed keys and reset automatically at the end of their windows.
- Exact signed mutation retries match a stored receipt and return the stored original success or error outcome. Rotation/revocation snapshots are never rewritten to current state; the independent authoritative revocation gate still runs before a signed replay can execute. Request-ID reuse with different bytes fails closed.
- Paired local submission remains `paired_self_controlled`, not remote attestation or provider-verified execution.
